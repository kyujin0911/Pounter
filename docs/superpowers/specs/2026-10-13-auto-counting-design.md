# 비AI 자동 계수 상세 설계

확정일: 2026-10-13. 상태: 사용자 승인 상세안 문서화 / 구현·현장 인수 미완료.

2026-10-13 추가 현장 사진 2장의 관찰과 사용자 정정을 보완했다. 사진 출처는 사용자 진술, 형상·배경 설명은 시각 관찰이며 정답 위치·검출 성능은 별도로 확인한다.

사용자는 기존 문서에 근거한 최우선 기능 설계, 상세 설계 진행, 해당 상세안의 설계 문서 확정을 요청했다. 이번 승인 범위는 설계 문서 작성·검토와 새 브랜치에서의 로컬 문서 커밋이다. 앱 구현·검출 실험·원격 push·PR 생성·병합은 포함하지 않는다. 작성된 문서의 사용자 검토 후 구현 계획으로 이어간다.

## 1. 목적과 근거

정면에 가까운 한 묶음 사진에서 식별 가능한 파이프 단면마다 자동 표시 하나를 만들고, 사용자가 위치별 검토·보정을 거쳐 확인 완료 기록을 저장하도록 한다. 최우선 기능은 복합 OpenCV 검출기와 기존 검토·보정 흐름의 연결이다.

- [PRD](../../../PRD.md): 사용자 결정·지원 범위·보존 정책·인수 조건의 단일 기준.
- [자동 계수 설계](../../auto_counting.md): 채택한 원·타원 후보 생성 + 영역 정보 보완 + 단면 검증 + 중복 통합 접근.
- [화면 명세](../../design_spec.md): 분석 중·검토·저장·Navigation 정책.
- [코드 컨벤션](../../code_conventions.md): 책임·패키지·명명·영속 계약·Koin 연결.
- [Git 운영 규칙](../../git_workflow.md): 목적별 브랜치·문서 검증·로컬 커밋·원격 승인 범위.
- [검증 이력](../../verification.md): 과거 실행 결과이며 이 설계의 새 검출 성능 근거가 아님.

본 문서는 채택 접근의 상세화를 담당한다. 기존 문서의 과거 작업 승인 범위를 새 구현 허가로 바꾸지 않으며, 충돌 시 최신 명시적 사용자 정정과 PRD를 따른다.

### 기준 코드와 선행 관계

기준은 `refactor/3-koin-di`의 `478cb50809c5f89cab8604efac23d3e6ba537e3d`이다. `docs/auto-counting-design`을 해당 커밋에서 분리한다. 로컬 main은 `e30d20c398b756423a6c8a82cbfd9d2460f1e395`이며 원격 서버 최신 상태·병합 여부는 조회하지 않았다. 본 설계는 main에 없는 구조 정리와 Koin 연결 상태를 참조하므로 독립적인 main 기반 작업으로 보고하지 않는다.

기준 코드에서 사진 입력·수동 보정·저장·세 Navigation 목적지는 존재한다. `ValidationRequiredDetector`는 검증 대기 오류를 반환하고 OpenCV 4.12.0은 androidTest 의존성이다. Koin의 `AppModule`은 이미 `PipeDetector`를 singleton으로 등록한다. 상세안 제시 후 반영된 Koin 상태를 문서에 반영했으며 신규 DI 도입은 필요하지 않다.

### 추가 현장 사진 관찰 — 2026-10-13

이번 첨부 `사진 1.jpg`·`사진 2.jpg`는 사용자가 현장에서 촬영했다고 설명한 자료다. 이전 인터넷 참고 사진 2장과 동일 자료로 취급하거나 그 출처를 변경하지 않는다. 정답 위치·정답 개수·촬영 세션/묶음의 독립성은 아직 확인하지 않았다. 검출 연산·자동 계수 실험은 실행하지 않았다.

사용자에게 노란 환형 단면과 금속색 단면을 모두 포함하는지 질문했다. 첫 답변은 기준이 다르다는 선택이었으나, 사용자가 "둘다야 아까 내가 잘못 보냈어"라고 정정했다. 최신 정정에 따라 두 종류 모두 계수 대상에 포함한다. 노란 부분의 재질·부품 역할은 확인되지 않았으므로 마개·라벨·도장이라고 단정하지 않는다.

| 자료 | 시각 관찰 | 설계·검증에 반영할 사항 |
|---|---|---|
| 사진 1 | 전경 묶음의 단면이 사진 일부에 모여 있고 바닥·장비가 넓게 포함됨. 노란 환형 단면 사이에 금속색 단면이 보임. 안/밖 경계·인접 단면·밝은 반사가 존재 | 화면 전체 축소와 실제 단면 픽셀 크기를 구분. 노란색만 찾는 방식의 누락, 내부 구멍/외부 테두리 중복, 인접 단면 통합 오류 평가 |
| 사진 2 | 전경에 더 많은 단면이 밀집하고 중심 위치·겉보기 크기가 일정하지 않음. 노란 단면과 금속색 단면이 함께 보임. 뒤쪽과 양옆에도 다른 묶음의 단면이 보임 | 주변 묶음 혼입, 노란 단면과 금속색 단면의 검출 차이, 밀집 경계 연결·깊이 차이로 생기는 실패를 별도 기록 |

첨부 파일 크기는 각각 960×1280px, 1280×960px이다. 이는 수신한 파일 크기이며 촬영 원본 해상도·카메라 설정으로 일반화하지 않는다. 두 사진만으로 돌출/후퇴 깊이·물리 규격·최대 300개·5%·5초 목표의 충족 여부를 확정하지 않는다.

다음 기준으로 기존 접근을 보완한다:

- 색상은 보조 근거로만 검토한다. 노란색이 없다는 이유로 금속색 단면을 버리지 않는다. 색상 기반 보완을 시험하면 색상 사용/미사용 결과를 같은 자료에서 비교한다.
- 한 파이프의 안쪽 구멍·노란 환형 부분·바깥 경계를 별개 파이프로 세지 않는다. 두 경계의 관계를 평가하되 완전한 고리나 노란색을 필수 조건으로 만들지 않는다.
- 한 묶음 계수 범위를 유지한다. 주변 묶음의 단면은 원형이라는 이유만으로 대상에 포함하지 않는다. 기본 탐색은 기존 문서대로 자동 후보 탐색이며 전경 묶음을 알고리즘이 자동 선택했다고 가정하지 않는다.
- 선택적 사각형 영역이 주변 묶음 혼입을 충분히 줄이는지 평가한다. 묶음의 불규칙 외곽/틈 때문에 배경 단면이 영역 안에 남는 경우를 확인한다. 해결되지 않으면 실패 사례와 촬영 구도 변경을 먼저 설명하고, 추가 선택 기능은 사용자와 별도 결정한다. 사진을 받았다는 이유로 필수 영역 지정·다각형·여러 묶음 자동 분리를 채택하지 않는다.
- 정답 규약에는 대상 단면 위치와 주변 묶음의 제외 대상을 함께 표시한다. 대상의 노란/금속색 조건을 구분해 누락·오검출을 보고하고 색상 하나의 성공을 전체 성공으로 확대하지 않는다.
- 설계에 사용한 두 사진은 오류 유형 탐색 자료다. 파라미터나 구현 선택에 활용하면 튜닝 자료로 관리하며 독립 검증 합격 자료로 동시에 사용하지 않는다. 추가 촬영 세션·묶음 자료가 필요하다.

사진 자체·사람이 포함된 원본·첨부 경로·오버레이를 저장소에 복사하거나 커밋하지 않는다. 이번 반영은 텍스트 관찰과 설계·검증 항목만 변경한다.

## 2. 범위와 완료 상태

핵심 흐름은 사진 확인 → 자동 분석 → 위치 표시 → 사용자 보정 → 확인 완료 저장이다.

포함 범위:

- 복합 OpenCV 후보 생성·검증·중복 통합·좌표 복원.
- 분석 취소, 늦은 결과 차단, 재분석 시 기존 결과 보존.
- 자동 결과의 저장 실패 재시도와 기존 기록 호환성.
- 독립 실사진 평가와 대표 기기에서의 앱 연결 검증.
- 사진 가져오기 축소로 작은 단면 정보가 사라지는지 평가하고, 원인으로 확인되면 관련 해상도 정책 수정.

단일 app 모듈과 기존 Repository·화면 ViewModel·Navigation 목적지를 유지한다. 신규 DI 라이브러리·UseCase·전역 Store·백그라운드 실행 체계·검출 강도 슬라이더는 추가하지 않는다. AI·숨은 개수 추정·여러 묶음 분리 등 제외 범위는 PRD를 따른다.

| 상태 | 판단 기준 |
|---|---|
| 검출 구현 완료 | 후보 생성·검증·통합·좌표 복원과 실패 처리가 동작 |
| 앱 연결 완료 | 분석·취소·보정·저장·복원·호환성 검증 통과 |
| 현장 인수 통과 | 독립 실사진과 대표 기기에서 PRD 인수 조건 충족 |

앞의 두 상태만으로 자동 계수 MVP를 완료 처리하지 않는다. 300개·보정량 5%·분석 5초는 지원 목표이며 현재 달성 성능이 아니다.

## 3. 구성과 데이터 계약

| 구성 | 책임 |
|---|---|
| `data/local/photo/PhotoStore` | 저장 사진 읽기와 분석 입력 준비. 미리보기와 분석 해상도 구분 |
| `data/detector` 복합 검출기 | 전처리·후보 생성·검증·통합·좌표 복원·자원 해제. UI 의존성 없음 |
| `LocalCountRepository` | 검출 호출·작업 결과 저장·revision·파일/DB 복구 |
| `CountViewModel` | Action·분석 Job·결과 유효성·저장 대기·불변 UiState 전환 |
| 기존 계수 화면 | 생명주기 기반 상태 수집·사진/표시·보정·진행·실패·재시도 |
| 기존 `AppModule` | 검출 구현체의 생성·singleton 수명 연결. 처리 로직은 포함하지 않음 |

`PipeDetector.detect(task)` 경계를 재사용한다. 검출에는 작업 사진과 영역의 시작 시점 스냅샷을 전달한다. 성공 결과는 최종 자동 표시 목록, 처리 소요 시간, 처리 버전을 포함한다. 현재 `Detection`을 확장하되 일반 화면에서 OpenCV 타입을 직접 사용하지 않는다.

내부 후보는 중심·타원 축/각도·생성 경로·경계 지지·형태 적합도·대비 근거를 유지한다. 후보를 기존 `Marker`와 혼동하지 않는다. 후보 근거와 탈락 이유는 평가 산출물에 남기고 일반 기록에 모든 중간 후보·이미지를 영속화하지 않는다. 평가 사진·개인 경로는 Git에 넣지 않는다.

최종 표시 ID는 중복 통합 후 한 번 생성한다. 저장·보정·재열기 동안 유지한다. 재분석 결과에는 새 ID를 부여하며 이전 보정의 ID를 임의로 대응하지 않는다.

성공과 실패의 의미:

- 분석을 정상 완료해 표시가 없는 경우만 성공한 0개 결과다.
- 사진 읽기·입력 준비·OpenCV 초기화·처리 실패는 구분된 실패 사유로 전달한다.
- 후보 처리 상한 도달과 최종 300개 초과는 각각 구분된 실패다. 부분 목록을 정상 성공 결과로 반환하지 않는다.
- 코루틴 취소는 오류 메시지용 일반 실패로 변환하지 않는다.
- 실패 사유에 맞춰 재시도·영역 확인·사진 교체를 안내한다. 품질을 자동으로 보증하는 문구는 쓰지 않는다.

## 4. 검출 처리

1. **입력 준비:** 방향 보정된 저장 사진을 읽고 선택 영역을 준비한다. 실제 영역 픽셀 시작점·크기·축소 배율을 함께 기록한다.
2. **전처리:** 그레이스케일과 최소한의 잡음 제거부터 시작한다. 밝기·반사·작은 단면 손실을 비교한다.
3. **형태 후보:** 윤곽에서 원·타원 후보를 생성한다. 경계 단절과 인접 단면 연결을 실패 유형으로 구분한다.
4. **영역 후보:** 국소 밝기 분리와 연결 영역으로 형태 후보의 누락을 보완한다. 내부가 항상 어둡다고 가정하지 않는다.
5. **단면 검증:** 경계 지지·형태 적합도·주변 대비·크기·다른 후보와의 관계를 함께 평가한다. 완벽한 원이나 완전한 경계 하나만을 합격 조건으로 삼지 않는다.
6. **중복 통합:** 이중 테두리와 두 생성 경로의 중복을 통합한다. 중심 거리뿐 아니라 경계 포함 관계·축 크기·겹침·생성 근거를 확인한다.
7. **출력 복원:** 남은 후보를 전체 저장 사진 기준 정규화 표시로 변환하고 안정적인 ID를 부여한다.

돌출·후퇴로 겉보기 크기가 다른 단면을 대표 반경 하나로 제거하지 않는다. 물리적 지름이 비슷해도 한 평면·동일 픽셀 크기를 전제하지 않는다. 작은 인접 단면 두 개를 하나로 합치는 오류를 별도 평가한다. 현재 거리 중심 `suppressConcentric`를 복합 검출의 검증된 통합 규칙으로 그대로 채택하지 않는다.

Hough는 비교 기준 또는 실제 개선이 확인된 보조 후보로 둔다. CLAHE·Watershed·겹치는 분할 분석은 실패 사례에서 필요성과 개선이 확인될 때만 추가한다. 분할을 추가하면 조각 경계의 누락·중복과 시간 증가도 평가한다.

전처리·크기 범위·후보 점수·통합 임계값은 튜닝 자료에서 정해 하나의 처리 버전으로 고정한다. 고정 구성은 검출기에 주입하고 사용자가 사진마다 조절하지 않는다. 독립 검증 자료를 보고 조정하면 새 버전과 새로운 독립 자료가 필요하다. 수치가 자료 기반 기술 선택이라는 이유로 사용자 확정 성능처럼 기록하지 않는다.

## 5. 방향 보정·해상도·좌표

### 방향 보정된 저장 사진의 의미

사진의 EXIF 회전·좌우 반전 정보를 실제 픽셀에 적용해 앱 전용 저장소에 복사한 사진이다. 갤러리가 회전 정보를 해석해 보여주는 방향과 분석 픽셀 방향을 일치시키는 처리다. 원본 갤러리 사진은 변경하지 않는다.

비스듬하게 촬영된 파이프의 원근을 펴거나 타원을 원으로 바꾸는 처리는 아니다. 단면들이 같은 평면에 있다고 가정하는 원근 보정도 기본 단계에 넣지 않는다.

### 해상도

기준 코드의 가져오기 과정은 긴 변 3000px 기준의 샘플 축소와 JPEG 저장을 사용하며, 미리보기 기본값은 긴 변 2048px이다. 이는 기존 구현 수치이며 검출 지원 해상도 확정값이 아니다. 검출에 미리보기 Bitmap을 재사용하지 않는다.

튜닝 자료에서 원본과 저장 사진의 단면 픽셀 크기·경계 보존·누락을 비교해 가져오기 손실과 분석 축소 손실을 구분한다. 가져오기 손실이 원인이면 보존 해상도·메모리·용량 정책을 이 기능의 관련 변경으로 수정한다. 분석 축소 손실만 있으면 분석 입력부터 조정한다. 기존 저해상도 사진을 확대해 원래 정보를 복원한 것으로 취급하지 않으며 필요하면 재가져오기/재촬영을 안내한다.

최소 단면 크기·지원 입력 크기·자원 상한은 실사진과 메모리 평가로 정하고 검증 버전에 기록한다. 자원 상한을 넘는 입력은 명시적으로 실패 처리하며 몰래 더 축소해 성공으로 반환하지 않는다.

### 좌표

전체 방향 보정 저장 사진을 좌표 기준으로 통일한다. 분석 좌표에서 축소 배율을 역변환하고 실제 영역 시작점을 더한 뒤 사진 전체 너비·높이로 각각 정규화한다. 영역의 반올림된 실제 픽셀 범위를 사용해 오차를 추적한다. 영역 경계 포함 규칙은 기존 `Region.contains`와 일치시킨다.

타원 축·각도는 내부 검증에 사용한다. 기존 `Marker`에는 정규화 중심과 표시용 반경을 전달한다. 반경은 사진 너비 기준 정규화 값이며, 타원의 짧은 반축을 기본 표시 크기로 사용한다. 화면의 표시 크기 조절·탭 영역은 검출 기하학과 구분한다. 원형 표시는 정확한 분할 경계를 뜻하지 않는다.

## 6. 상태·취소·재분석

기존 `Operation.ANALYZING → SAVING → NONE`과 읽기 전용 `StateFlow<CountUiState>`를 사용한다. Compose는 `collectAsStateWithLifecycle`로 수집하고 Action을 전달한다. 허위 진행 백분율은 표시하지 않는다.

1. 미저장 변경이 없는 미확정 작업에서 시작한다. 보정이 교체되는 재분석은 먼저 확인받는다.
2. 작업 ID·revision·사진·영역·분석 세대를 고정한다. 기존 표시를 지우지 않는다.
3. 분석 중 편집·영역 변경·완료 확정을 차단하고 취소를 제공한다.
4. 결과를 받은 뒤 코루틴 활성 상태와 현재 작업/세대를 확인한다. 시작 시점의 사진·영역·revision도 비교한다.
5. 유효한 결과만 새 작업 스냅샷으로 만들고 저장 대기 경로로 넘긴다.
6. 저장 시작 이후 취소를 제공하지 않는다. 저장 성공 후 검토·보정을 허용한다.

취소는 분석 세대를 무효화하고 기존 표시를 유지한다. 늦게 반환된 결과는 반영하지 않는다. 검출기 singleton의 실행 잠금으로 한 번에 한 분석만 실행한다. 취소 후에도 네이티브 호출이 남아 있다면 새 요청은 잠금 대기 상태에서 이전 처리가 끝나기를 기다리고 이 상태를 문구로 알린다.

네이티브 호출이 코루틴 취소로 즉시 중단된다고 가정하지 않는다. 잠금 대기와 단계 사이에서 취소를 확인하고 `finally`에서 Bitmap·Mat을 해제한 뒤 잠금을 반환한다. 초기화도 동일한 실행 경계에서 처리한다. 새 분석 대기 시간을 사용자 관찰 지연에서 제외하지 않는다.

화면 이동/entry 해제와 OS 프로세스 종료 후 중단된 연산은 자동 재개하지 않는다. 저장된 작업을 복원하고 사용자가 분석을 다시 요청하도록 한다.

영역 변경 확인은 기존 화면 명세를 따른다. 검출기 자체가 영역 변경이나 기존 보정 삭제를 수행하지 않는다.

## 7. 저장·복원·호환성

자동 결과도 일반 편집과 같은 `taskPendingSave`·`pendingSave` 저장 대기 경로를 사용한다. 현재 분석의 별도 직접 저장 경로를 이 정책으로 통합하는 것이 관련 수정 범위다.

| 상황 | 동작 |
|---|---|
| 분석 실패·취소 | 기존 저장 결과·보정 유지 |
| 분석 성공·저장 중 | 새 결과를 저장 대기 스냅샷으로 보존 |
| 저장 실패 | 새 표시를 미저장 상태로 유지하고 저장 재시도 제공 |
| 미저장 상태 | 재분석·추가 보정·완료 확정 차단. 저장된 값과 구분 |
| 저장 성공 | 저장 대기 값 제거, Repository가 반환한 revision 반영 |
| revision 충돌 | 조용한 덮어쓰기 없이 실패 안내. 기존 저장 기록 보존 |

저장 성공 확인 전에는 사용자 확인 완료로 표시하지 않는다. 작업 복원 시 저장 대기 값이 이미 DB에 반영됐는지 비교하는 기존 정책을 유지한다. OS가 저장 상태를 복원해 주는 경우의 미저장 스냅샷 복원과 강제 종료 후 DB 재열기를 구분한다. 저장 전 데이터가 모든 종료 상황에서 영속 보존된다고 주장하지 않는다.

`automatic`은 분석 원본, `markers`는 보정 후 유효 표시로 유지하고 최종 개수는 `markers.size`에서 계산한다. 자동 제외는 원본 ID와 유효 ID의 차이, 수동 추가는 `manual`로 구분한다. 현재 마지막 보정 되돌리기를 유지하며 별도 전체 편집 이력 DB는 추가하지 않는다.

처리 버전은 선택적 `analysisMetadata`에 저장한다. 기존 `analysisMillis`는 검출 처리 소요 시간으로 유지한다. `analysisMetadata`가 없는 기존 기록은 null로 읽으며 새 검출 버전으로 처리된 기록이라고 해석하지 않는다. 새 수동 작업에는 자동 분석 메타데이터를 부여하지 않고, 영역 초기화에서는 이전 분석 메타데이터도 제거한다. 자동 결과를 수동으로 보정할 때는 해당 자동 분석 메타데이터를 유지한다.

기존 JSON key·Room 컬럼·DB 버전·Navigation 인자·복원 key는 유지한다. 메타데이터는 기존 payload 안의 선택 필드로 추가하므로 Room 컬럼 변경을 요구하지 않는다. `TaskCodec`의 이전 payload 읽기와 Kotlin 직렬화의 이전 `pendingSave` 읽기를 각각 검증한다. 기존 데이터 초기화나 파괴적 마이그레이션은 사용하지 않는다.

## 8. 검증과 제공 순서

검출 구현은 우선 평가용 연결로 검증한다. 현장 인수 전 앱의 기본 Koin 등록은 검증 대기 구현체로 유지하고, 평가 환경에서 같은 `PipeDetector` 계약으로 복합 검출기를 연결한다. 테스트 결과나 런타임 플래그만으로 현장 합격을 대신하지 않는다. 앱 기본 등록 변경과 OpenCV 런타임 의존성 전환은 이후 승인된 구현 범위에서 검토한다.

| 검증 구분 | 확인 내용 |
|---|---|
| 좌표·통합 | 회전/반전 입력, 영역 경계·비정사각 사진·축소 역변환, 이중 테두리 통합, 인접 단면 유지 |
| 실패·자원 | 읽기/초기화 실패, 후보 포화·300개 초과, 실제 0개, 취소 중 Mat 해제·새 분석 직렬 실행 |
| 상태·저장 | 늦은 결과 차단, 재분석 실패 보존, 저장 실패 재시도, revision 충돌, 중복 완료 |
| 호환성 | 과거 기록·복원 스냅샷, 자동/수동 출처·메타데이터·표시 ID 재열기 |
| 실사진 | 위치별 누락·오검출·보정량, 정렬·돌출/후퇴·반사·고밀도·부분 가림별 결과 |
| S22+ / Android 16 | 초기화·분석·표시 시간, 메모리, 취소/재시도, 전체 검수 시간 |

실제 현장 사진 2장은 추가로 제공되어 설계 참고에 반영했다. 단면별 정답 위치·개수·촬영 세션 구분과 추가 독립 자료는 여전히 필요한 입력이다. 노란 단면·금속색 단면 모두 포함한다는 최신 사용자 정정을 정답 규약에 반영하고, 대상 묶음의 위치 범위와 주변 단면 제외를 표시한다. 인터넷 참고 사진이나 이번 두 장만으로 독립 현장 인수를 대신하지 않는다. 초기 튜닝 10장/독립 검증 10장은 PRD의 가능성 탐색 제안 규모이며 일반적인 현장 성능 보장 수량이 아니다.

촬영 세션·묶음 기준으로 자료를 분리하고 결과 확인 전에 정답 위치·지원 여부·부분 가림 포함 범위를 고정한다. 단면과 표시를 일대일 대응하며, 합계가 같아도 누락과 오검출을 각각 기록한다. 작은 불규칙 파이프군의 실패를 평균으로 숨기거나 지원 밖으로 일괄 제외하지 않는다.

PRD 인수 조건을 유지한다:

- N > 0인 각 사진의 누락 추가 + 오검출 삭제는 `max(1, floor(N × 0.05))` 이내. 같은 표시 삭제 후 추가는 2회로 센다.
- 보정·사용자 확인 후 최종 개수와 정답 일치. 소량 최소 1회 허용 결과는 별도 보고.
- N = 0은 별도 평가하고 오검출 허용값을 정답 규약에 명시. 자동 확정 금지.
- 분석 시작부터 표시 생성까지 5초 목표. 검출 내부 시간과 저장·화면 반영·잠금 대기를 포함한 사용자 관찰 시간을 따로 측정한다. 첫 초기화 비용을 별도 기록한다.
- 촬영·자르기·분석·검토·보정·재촬영 전체 시간과 최종 오류를 기존 수동 방식과 비교. 필요 개선 폭·반복 횟수는 첫 사용 실험 후 합의한다.

합성 이미지 테스트는 기하학·통합·상태 검증 자료이며 현장 합격 근거가 아니다. 회전/Activity 재생성, OS 프로세스 종료, 강제 종료 재실행을 각각 검증한다. 실행하지 않은 항목은 미검증으로 남긴다.

## 9. 후속 단계와 문서 검토

상세안은 사용자 승인 방향을 기록한 설계이며 실제 성능 확정이 아니다. 처리 수치·해상도·자원 상한은 지정한 튜닝/기기 평가 단계에서 정하는 기술 선택이다. 실사진·정답 미확보 상태에서 현장 인수 완료를 선언할 수 없다.

문서 저장 후 링크·범위·기존 기록 호환성·상태 전환·검증 기준을 자체 검토하고 문서 파일만 로컬 커밋한다. 작성된 문서를 사용자가 검토·승인하면 `writing-plans`로 구현 계획을 작성한다. 계획 검토와 실행 방법 선택 전에는 앱 구현을 시작하지 않는다.
