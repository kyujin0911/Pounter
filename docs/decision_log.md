## D-01 목적과 입력

- 날짜/상태: 2026-10-12 / 사용자 확정.
- 결정: 작은 Android 네이티브 앱을 완성해 개발 방식을 체험. 사진 선택+시스템 카메라 촬영 후 정지 사진 분석, 기기 내부 처리, 자동 후 사람 보정.
- 이유/대안: 실시간은 프레임·흔들림·발열 대응 추가. 사진 선택만으로 축소하는 대안 대신 두 입력 선택. 포트폴리오·상용 운영·서버·계정 제외.
- 적용: PRD R-01~R-03. 사진당 외부 API·모델 구독을 전제하지 않음.

## D-02 한 묶음 촬영 조건 정정

- 날짜/상태: 2026-10-12 / 사용자 정정 확정.
- 결정: 인터뷰 결과 한 묶음만 촬영할 수 있음. 여러 묶음이 함께 찍히는 것이 흔하다는 이전 답변은 대체.
- 영향: 필수 대상 묶음 선택·자동 묶음 분리 요구 제거. 배경 자르기는 선택 기능으로 유지하는 설계 제안. 이전의 한 영역씩 여러 묶음 선택·다각형 영역 우선 제안은 현재 MVP에서 비채택.
- 재제안 조건: 향후 실제 사용에서 한 묶음 촬영이 불가능하다고 확인되면 범위 재논의.

## D-03 불규칙한 끝과 자료의 출처

- 날짜/상태: 2026-10-12 / 사용자 확인 사실, 지원 성능 검증 대기.
- 결정: 작은 파이프의 돌출·후퇴를 검증 범위에 포함. 동일 평면·겉보기 동일 크기 가정 제거. 정면 조건을 모든 기울어진 사진 지원으로 확대하지 않음.
- 자료: 초기3장은 현장 촬영 참고, 이후2장은 인터넷에서 찾아 현장 유사성을 사용자에게 확인한 자료. 실제 현장 촬영·정답·성능 증거로 합치지 않음. 자세한 자료 경계는 PRD.
- 이유: 끝이 불규칙해도 개별 단면을 식별할 수 있는 상황에 맞춰야 함. 완전히 숨은 파이프 추정은 계속 제외.

## D-04 자동 계수 접근 채택

- 날짜/상태: 2026-10-12 / 이번 사용자 요청에서 확정.
- 결정: 비AI OpenCV의 원·타원 후보 생성 + 영역 정보 보완 + 단면 검증 + 중복 통합.
- 이유: 정면 한 묶음 조건, 돌출/후퇴·반사에 필요한 후보 검증, 기기 내부 실행, 학습/라이선스/클라우드 비용 부담을 함께 고려.
- 대안: 단순 Hough는 비교 기준. 윤곽/타원·밝기 후보 세부 조합은 설계 제안. Watershed·분할은 실제 오류가 필요성을 입증할 때만 추가. Kotlin/GPU 직접 구현은 개발 부담으로 비채택.
- 비채택 이력: YOLO26n+LiteRT는 AI 허용 시 제안이었고, YOLOX+ONNX Runtime은 비용·비공개 배포 고려 시 차선책이었다. 사용자 구현 승인·모델 구매 결정이 아니며 최신 비AI 선택에서 제외. 학습 GPU 예산 제안도 활성 예산으로 쓰지 않음.
- 재제안 조건: 비AI 방식이 독립 검증에서 기준을 충족하지 못하고 사용자가 AI/범위 변경 논의를 요청·허용한 경우. 무료 라이브러리나 시중 앱의 존재는 성능 증거가 아님.

## D-05 성능 목표와 검증 상태

- 날짜/상태: 2026-10-12 / 사용자 목표 확정, 달성 여부 미검증.
- 결정: 최대300개, 보정량5% 이내·소량 최소1회 허용, 대표 실기기5초. 정확한 측정 정의는 PRD 인수 조건 한 곳에 둠.
- 제안: 초기20장 분리 평가는 가능성 탐색 규모. 전체 검수 시간·최종 오류 비교를 추가. 0개 자료 규약·반복 횟수·필요 개선 폭은 실제 검증 설계에서 정함.
- 경계: 합성12개 원형 테스트, 기울어진3장 단순 Hough 실패, 과거 앱 테스트는 최신 복합 검출 합격 근거가 아님. 정렬군만 통과했을 때 불규칙 작은 파이프를 완료로 확대하지 않음.

## D-06 보존·완료·실패 정책

- 날짜/상태: 2026-10-12 / 로컬 기록·작업 보존·기록별 삭제는 사용자 확정. 세부 정책은 임시 기본값.
- 기본값: 앱 내부 사진 복사·원본 불변, 자동 만료 없음, 백업 제외, 읽기 전용 사용자 확인 완료 기록, 오확정 삭제 후 새 작업. 소실/삭제 안내. 자세한 동작은 PRD.
- 이유: 데이터 손실·중복 완료 방지, 기록 대조 가능성. 종료 시 폐기·현재1건만 보존은 사용자 미선택. 업무 증빙·정정 이력·이름 입력은 미채택.
- 대체 제안: 완료 문구는 '사용자 확인 완료'. 기존 '확정됨' 표기를 객관적 정확성 보장처럼 쓰지 않음.

## D-07 구조·디자인

- 날짜/상태: 2026-10-12 / Kotlin·Compose·MVI는 사용자 제약. 단일 모듈·Room·생성자 주입은 구현 기본값.
- 이유: 작은 앱에서 책임과 상태 흐름 명확화. 별도 Store·DI/MVI 프레임워크·UseCase·모듈은 현재 필요성 없음.
- 디자인: 사진·개수·상태 우선. 레퍼런스는 표시/보정/저장 구조에 활용하며 내부 검출 알고리즘을 화면으로 확정하지 않음. 수치·색상·표시 모양은 디자인 제안. 상세는 화면 명세.
