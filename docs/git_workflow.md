# Pounter Git 운영 규칙

갱신일: 2026-10-12. Issue·브랜치·커밋·PR·병합 규칙의 단일 기준이다. 제품 요구는 [PRD](../PRD.md), Codex 실행 경계는 [AGENTS](../AGENTS.md)를 따른다. 아래 명령·메시지는 사용 예시이며 실제 실행 증거가 아니다.

## 확인한 상태와 채택 이유

이번 시작 시 로컬 main은 db5490e이며 저장된 origin/main과 차이가 0/0이었다. origin은 kyujin0911/Pounter 저장소로 등록되어 있다. 원격 조회/fetch는 하지 않았으므로 GitHub 서버의 최신 상태와 기본 브랜치·보호 규칙은 미확인이다. 로컬 .github 템플릿·CI 파일, commit.template 설정은 없었다. 이전 영문 커밋과 기존 브랜치 이력은 그대로 보존한다.

GitHub Flow를 유지한다. 소규모 개인 체험 앱에는 main과 목적별 작업 브랜치로 충분하며 develop/release/hotfix를 추가하지 않는다. main에 반영된 앱 품질과 자동 계수의 현장 성능은 별도이며, 미검증 기능을 완료로 보고하지 않는다.

## Issue 규칙과 템플릿

기본 작성 언어는 한국어, 제목은 type(scope): 구체적인 목적/증상으로 한다. type은 커밋 규칙을 재사용하고 scope는 선택이다. 버그는 fix, 기능은 feat, 구조 개선은 refactor, 문서/빌드 작업은 docs/build 등으로 구분한다. 제목의 성과 수치와 원인 확정은 실제 근거가 있을 때만 쓴다.

- 먼저 같은 목적/증상의 기존 Issue를 찾고 적합하면 보완한다. 작은 오타·명확한 단일 문서 수정까지 Issue 생성을 강제하지 않는다. 기능·재현 버그·설계 선택·여러 단계의 검증 작업은 Issue로 목적을 남긴다.
- Issue 하나는 독립적으로 완료 조건을 판정할 수 있는 목적이다. 파일/커밋 개수로 나누지 않는다. 코드 구조 정리와 Koin처럼 검증·위험·되돌림 기준이 다르면 별도 Issue를 만들고 선행 관계를 연결한다.
- [.github/ISSUE_TEMPLATE/01-work.md](../.github/ISSUE_TEMPLATE/01-work.md): 기능·리팩터링·문서·빌드·기술 조사용. 목적, 범위, 완료 조건, 검증 계획, 필요할 때 관련/제약을 적는다.
- [.github/ISSUE_TEMPLATE/02-bug.md](../.github/ISSUE_TEMPLATE/02-bug.md): 기대/실제 동작, 재현 절차, 코드/실행 환경, 완료 조건, 근거를 적는다. 재현·원인·환경이 미확인이면 그대로 표시한다.
- 완료 조건의 체크박스는 미래 작업의 조건이다. 실제 확인한 뒤에만 체크한다. 검출 실험은 앱 통합 완료와 구분하고 사진 출처·독립 자료·정답 위치·누락/오검출·시간 정의를 PRD에 맞춘다.
- 개인정보·키·현장 사진·개인 경로는 Issue에도 올리지 않는다. 최소 재현 대역과 민감 내용 제거한 로그를 사용한다.
- 상태는 본문/댓글에서 검토 중→진행 중→검증 대기→완료/취소를 설명한다. GitHub Issue는 open/closed와 종료 이유로 관리하며 실제 Draft 기능이 있다고 가정하지 않는다. 별도 Project·상태/우선순위 라벨·자동 담당자는 강제하지 않는다.
- 열린 Issue가 작업 요청/승인 범위를 대신하지 않는다. 실제 사용자가 허용한 코드/원격 동작만 수행한다. Codex가 GitHub Issue를 작성·수정하는 경우도 해당 요청 범위를 확인한다.

Issue 기반 작업의 브랜치 예시: codex/123-save-retry. 실제 Issue가 없으면 기존 codex/save-retry 형식을 사용하며 번호를 만들어 쓰지 않는다. 기본은 목적별 Issue→작업 브랜치→커밋→PR이다. 한 Issue를 여러 PR로 나눌 때 남은 완료 조건과 의존 관계를 명시한다.

PR/중간 커밋에서 진행을 연결하려면 Refs: #실제번호를 사용한다. 완료 조건 전부를 해결하는 최종 PR에만 Closes #실제번호를 적는다. 기본 브랜치 병합 후 자동 종료 여부와 잔여 검증을 확인한다. 단순 커밋·PR 생성·AI 리뷰 통과로 Issue를 완료 처리하지 않는다. 취소/중복은 이유와 대체 Issue를 남긴다.

템플릿은 기본 브랜치의 .github/ISSUE_TEMPLATE에 반영해야 새 Issue 선택 화면에서 사용된다. [config.yml](../.github/ISSUE_TEMPLATE/config.yml)은 자유 작성도 허용한다. Markdown 템플릿은 필수 입력을 자동 강제하지 않으므로 제출 전 목적/재현·완료 조건을 검토한다. 자동 라벨·담당자나 관련 설정을 이번에 추가하지 않는다. 실제 Issue 생성 없이 템플릿 등록 파일을 검증하고 GitHub 기본 브랜치에서 확인한다.

## 작업 순서와 브랜치

1. 요청 범위·현재 브랜치·변경·관련 지침을 확인한다. 사용자 변경은 보존하고 자동 stash/reset/clean으로 작업 공간을 비우지 않는다.
2. 기준 main에서 codex/ 작업 브랜치를 만든다. 변경·관련 검증·diff 검토 후 목적 단위로 로컬 커밋한다.
3. 사용자 요청에 push가 포함되면 해당 브랜치를 올린다. PR 생성 요청이 있으면 main 대상 PR을 작성한다. 미완료/핵심 검증 대기는 Draft로 표시한다.
4. 변경 최종 상태를 리뷰하고 관련 검증과 미검증을 확인한다. 병합 요청이 있을 때만 Squash merge한다.
5. 이후 main을 갱신하고 다음 작업은 새 브랜치에서 시작한다. 브랜치 정리는 아래 규칙을 따른다.

### 이름·시작점·재사용

- 기본 형식: codex/<짧은-작업명>. 소문자 ASCII·숫자·하이픈을 쓰며 목적을 나타낸다. 예: codex/save-retry, codex/photo-import, codex/git-workflow.
- 한 브랜치는 하나의 리뷰 가능한 목적이다. 그 목적에 필요한 코드·테스트·문서는 함께 변경할 수 있다. 이슈 번호는 실제 이슈가 있을 때만 선택적으로 포함한다.
- 기본 시작점은 최신 확인된 main이다. 원격 접근이 허용되면 fetch와 fast-forward로 갱신한다. 로컬 작업만 허용되면 현재 main SHA에서 시작하고 원격 최신 여부를 미확인으로 남긴다. 최신 기준이 필수인데 확인 불가하면 그 의존 작업만 진행을 보류한다.
- 진행 중인 같은 목적의 미병합 브랜치는 재사용한다. 다른 목적, 병합/종료된 브랜치는 새로 만든다. 특정 후속 작업이 미병합 변경에 의존하면 시작 SHA·의존 PR을 명시하며 독립 작업처럼 보고하지 않는다.
- 서로 따로 검증·리뷰·되돌릴 수 있는 목적이 추가되면 브랜치/PR을 분리한다. 단순히 파일 수가 많다는 이유만으로 나누지 않는다.

새 작업 예시(각 원격 명령은 허용된 경우에만):

```sh
git status --short --branch
git switch main
git fetch origin
git merge --ff-only origin/main
git switch -c codex/save-retry
```

main의 새 변경은 작업 브랜치에 git merge origin/main으로 가져온다. 이미 공유한 커밋을 재작성하지 않아 force push가 필요하지 않고 개인 프로젝트에서도 절차가 일관된다. 충돌 해결 후 영향 받은 검증을 다시 수행한다. Git이 생성한 동기화 merge 메시지는 커밋 제목 형식의 예외이며, PR의 최종 squash 제목은 아래 규칙을 따른다.

```sh
# 현재 작업 브랜치에서, 원격 접근이 허용된 경우
git fetch origin
git merge origin/main
```

rebase/amend/reset 등으로 공유 이력을 재작성하거나 force push하는 것은 명시적 승인 없이 하지 않는다. 과거 메시지를 컨벤션에 맞추기 위해 이력을 재작성하지 않는다.

### 최초 main이 없는 저장소

현재 Pounter에는 main이 있으므로 이 절차는 실행하지 않는다. 향후 저장소에서 main이 없다면 기존 이력과 관련 검증을 확인하고 기준 SHA를 선택한다. 사용자가 main 준비를 요청한 경우에만 git branch main 기준SHA로 생성한다. 최초 push는 별도 원격 작업 범위에 따라 수행하고, 원격이 빈 저장소인지 먼저 확인한다. main 생성·원격 등록·push를 문서 작성 승인에 포함시키지 않는다.

## 커밋 메시지

형식: type(scope): 한국어 변경 설명. scope는 생략 가능하다. type/scope는 소문자 영어, 제목·본문은 한국어를 기본으로 한다. 코드/API 이름은 원래 표기한다. 프로젝트 문서·사용자 설명과 언어를 맞추면서 Conventional Commits 형태를 유지한다.

| type | 기준 |
|---|---|
| feat | 사용자가 사용할 수 있는 기능 추가 |
| fix | 재현 가능한 잘못된 동작 수정 |
| refactor | 기능 동작을 유지하는 내부 구조 개선 |
| docs | 문서·문서 템플릿 변경 |
| test | 제품 동작 변경 없이 테스트 추가/수정 |
| build | 빌드 설정·플러그인·의존성 변경 |
| chore | 위 범주에 해당하지 않는 저장소 관리 작업 |

scope는 count, photo, navigation, storage 등 구분에 도움 되는 경우만 붙인다. 동작 수정에 동반한 테스트는 별도 test 커밋을 강제하지 않고 fix에 함께 포함할 수 있다. 독립 목적이 섞이면 커밋을 나눈다. revert가 필요한 경우 revert: 한국어 설명과 대상 SHA·영향을 기록한다. 자동 SemVer/릴리스 생성은 도입하지 않는다.

제목은 변경 결과를 구체적으로 쓰고 가능하면 72자 이내 한 줄로 작성한다. 마침표·불필요한 완료/성공 표현을 피한다. 본문은 제목으로 설명이 부족할 때만 빈 줄 뒤에 이유·영향·호환성·한계를 적는다. 검증을 적으면 현재 변경에서 실제 수행한 방법·결과만 쓴다. 실행하지 않은 검증은 미검증과 이유를 적고, 과거 기록은 해당 SHA/시점으로 구분한다.

! 또는 BREAKING CHANGE:는 사용자/소비자가 조정해야 하는 실제 호환성 파괴가 있을 때만 쓴다. 대규모 리팩터링이나 패키지 이동 자체로 붙이지 않는다. 앱 ID·기록 형식 변화의 실제 영향은 본문/PR에 설명한다. 실제 관련 이슈가 있으면 Refs: #번호, 해결 범위가 맞을 때만 Closes: #번호를 사용한다.

### 목적 단위와 예시

아래는 작성 예시이며 구현·실행 결과를 주장하지 않는다.

- fix(count): 저장 실패한 보정을 유지하고 재시도 — 상태 수정·복구 테스트·관련 설명을 함께 포함 가능.
- refactor(navigation): 목록과 계수 화면의 이동 책임 분리 — 동작 보존이 전제. 새 사용자 기능을 추가했다면 feat로 분류.
- docs: Git 운영 규칙과 커밋·PR 템플릿 추가 — 이번처럼 문서/템플릿이 하나의 목적.
- 피할 예: fix: 수정, chore: 여러 작업 정리, feat: 자동 계수 정확도 95% 달성. 구체적인 변경·검증 정의 없이 성과를 제목에 쓰지 않는다.
- 피할 묶음: 저장 실패 수정 + 무관한 테마 변경 + 의존성 전체 업데이트. 따로 리뷰/되돌릴 수 있는 목적은 분리한다.

스테이징은 파일을 명시하거나 부분 변경은 git add -p로 선택한다. git add . / git add -A를 기본으로 하지 않는다. 코드·문서와 무관한 사용자 파일·서명 키·현장 사진·오버레이·개인 경로는 포함하지 않는다. 공유/제외 기준은 [.gitignore](../.gitignore)를 따른다.

```sh
# 문서 작업 예시: 실제 변경한 파일만 선택
git add docs/git_workflow.md .github/pull_request_template.md .gitmessage
git diff --cached --check
git diff --cached
git status --short
git commit
```

[.gitmessage](../.gitmessage)는 편집 안내이며 형식을 자동 강제하지 않는다. 저장소 루트에서 사용자가 선택하여 로컬 설정한다. 이번 작업에서는 설정하지 않는다.

```sh
git config --local commit.template "$(git rev-parse --show-toplevel)/.gitmessage"
# 적용 확인
git config --local --get commit.template
# 해제하려면
git config --local --unset commit.template
```

설정은 로컬 절대 경로를 사용하므로 저장소를 이동했다면 다시 적용한다. 개인 경로는 공유 문서/커밋에 기록하지 않는다.

git commit -m 또는 --file로 메시지를 제공하면 템플릿 편집을 거치지 않을 수 있으므로 작성자가 규칙을 확인한다. Codex가 긴 본문을 만들면 정확한 개행을 가진 임시 파일과 --file을 사용한다.

## PR 작성과 완료 판단

PR 제목은 최종 목적을 나타내는 Conventional Commits 제목, 설명은 한국어를 기본으로 한다. [.github/pull_request_template.md](../.github/pull_request_template.md)를 사용한다. 사소한 변경은 변경 이유/결과와 검증을 몇 문장으로 쓰고, 불필요한 절은 삭제한다. 복잡한 변경만 구체적 재현 조건·전후 동작·설계 선택·데이터 영향을 추가한다. 대화 이력·포기한 시도·무관한 기술 설명은 제거하고 범위가 바뀌면 최종 변경 기준으로 제목/본문을 다시 쓴다.

검증에는 아래 중 적용되는 것만 실제 방법·결과를 기록한다. 일괄 체크박스로 모두 통과 처리하지 않는다.

- 문서/템플릿: 재독·로컬 링크·결정 상태·diff --check. 앱 빌드/기기 테스트는 해당 없음.
- Android 코드: 관련 빌드·Lint·JVM 테스트. 에뮬레이터는 AVD/API, 실기기는 모델/OS, UI 확인은 실제 확인 화면/범위를 별도로 기록한다. 회전·Activity 재생성·OS 프로세스 종료·강제 종료는 서로 대체하지 않는다.
- 자동 계수: 앱 동작과 검출 품질을 구분한다. 합성/인터넷 참고/실제 현장 자료, 튜닝/독립 검증, 위치별 누락·오검출, 처리/전체 검수 시간을 구분하고 [PRD 인수 조건](../PRD.md#5-인수-조건)을 따른다. 사진과 개인 경로를 PR/커밋에 첨부하지 않는다.
- 적용되는 미실행 검증: 이유·영향·다음 확인 절차를 명시한다. 과거 테스트·정적 코드 검토를 이번 실행으로 쓰지 않는다.

미완료 기능, 핵심 검증 대기, 미해결 실패는 Draft로 남긴다. ready는 관련 검증이 통과하고 필수 미검증이 해소되거나 제한된 범위가 사용자에게 명시적으로 수용된 상태다. 정확도 목표를 약화하거나 수동 계수를 자동 계수 완료로 바꿔 ready 처리하지 않는다.

병합 전 작성자는 최종 diff, 범위, 사용자 변경 보존, 비공개 파일, 관련 검증과 잔여 영향을 리뷰한다. 개인 프로젝트에서 외부 리뷰어 승인을 필수로 요구하지 않으며 Codex의 자기 검토를 인간 승인처럼 기록하지 않는다. CI가 없다면 로컬 검증과 미검증을 근거로 판단한다. 사용자에게 병합 허가가 있는지 별도로 확인한다.

### Squash merge와 이후 정리

기본 병합은 GitHub Squash merge다. 작업 브랜치에는 목적 단위 커밋을 남기고 main에는 리뷰한 PR 목적 하나를 최종 제목·설명으로 남긴다. 커밋의 중간 시행착오는 최종 설명으로 정리하되 필요한 검증 한계는 보존한다. GitHub가 만든 기본 squash 메시지는 그대로 사용하지 않고 PR 제목 컨벤션과 최종 동작을 확인한다.

squash 후 기존 작업 브랜치를 계속 사용하지 않는다. 최신 main에서 다음 브랜치를 만든다. 원격/로컬 작업 브랜치 삭제는 요청 범위에 포함될 때만 수행한다. git branch -d는 squash 때문에 거절될 수 있다. 이때 자동으로 -D로 바꾸지 말고, 병합 결과와 main 대비 잔여 변경·보존할 커밋을 확인한 뒤 명시적 삭제 승인에 따라 처리한다. main·미병합/다른 사용자 브랜치는 정리 대상이 아니다.

원격 push, PR 생성, 병합·브랜치 삭제는 각각 실제 사용자 요청 범위로 판단한다. 한 동작의 허가를 나머지 허가로 확대하지 않으며 문서 예시는 실행 허가가 아니다. 실제 PR을 만들면 작업에 PR 링크를 연결하고 완료 보고에 남긴다.

## 원격 설정 권고 — 미적용

권고: GitHub 기본 브랜치 main, PR을 통한 반영, force push·삭제 제한, Squash merge 허용. 개인 프로젝트에는 다른 사람의 승인 1회를 필수로 걸지 않는다. 필수 상태 검사는 실제 CI가 생긴 뒤 유효한 검사 이름으로 설정한다. 현재 CI·보호 설정은 확인/적용하지 않았으므로 작동 중이라고 보고하지 않는다.

PR 템플릿은 대상 기본 브랜치에 반영된 뒤 사용 여부를 확인한다. 로컬 .gitmessage 설정은 clone한 개발자가 선택한다. hooks·commitlint·Husky·새 CI는 현재 작성 부담보다 이점이 확인되지 않아 추가하지 않는다. Issue 템플릿은 이후 명시적 사용자 요청에 따라 위 두 종류를 추가한다. 반복되는 누락이나 실제 협업이 생기면 별도 요청으로 재검토한다.
